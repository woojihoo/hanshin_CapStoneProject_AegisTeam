# 가명 토큰 기반 문서 포렌식 마킹 시스템 (1학기 MVP)

스마트폰 화면 촬영·크롭·재압축을 거친 이미지에서도 **누구에게 배포된 사본인지** 추적하는 비가시성 워터마킹 시스템입니다.
문서에는 사번·이름 대신 **배포본별 무작위 24비트 가명 토큰**만 숨기고, 토큰↔사용자 대응은 해시 체인으로 묶인 발급 원장에 AES-GCM으로 암호화해 보관합니다.
추출한 토큰은 **발급된 토큰이고 기록이 바뀌지 않았다는 것이 함께 검증될 때만** 식별 근거가 됩니다.

> 이 코드는 2026 한국디지털콘텐츠학회 추계종합학술대회 발표 논문(우지호·최강의·박경모)의 설계 사양을 따릅니다.
> 이전 버전(48비트 토큰, Reed-Solomon, PN 확산 방식)은 팀장 로컬 폴더의 `_archive/v1_rs48/` 에만 보관하며 저장소에는 올리지 않았습니다.

## 폴더 구성

| 경로 | 내용 | 담당 |
|---|---|---|
| `wm_core/` | 워터마킹 엔진 (DWT LL·DCT 계수 쌍 삽입/추출, BCH(63,24), 다수결, 동기 템플릿, 원근 보정, 공격 시뮬레이션) | 우지호 |
| `backend/app/` | FastAPI REST API(`/issue` `/trace` `/verify`), 가명 토큰 발급, 해시 체인 발급 원장(AES-GCM), 감사 로그, PDF 처리 | 최강의 |
| `frontend/` | 관제 웹 UI (문서 등록·배포, 유출 역추적, 감사 로그) | 박경모 |
| `eval/` | 모의 공격 평가 스크립트와 결과(`eval/results/`) | 박경모 |
| `scripts/` | `cli.py`(서버 없이 삽입/추출), `gen_keys.py`(운영 키 생성) | 공통 |
| `tests/` | 단위·통합 테스트 | 공통 |

## 실행 방법

```bash
python -m venv .venv && source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt
uvicorn backend.app.main:app --reload                   # 프로젝트 루트에서 실행
```

브라우저에서 <http://localhost:8000> 을 열고 오른쪽 위에 관리자 API 키를 입력합니다.
환경변수 키가 없으면 처음 실행 때 `data/dev_keys.json` 이 만들어지며, 그 안의 `admin_key` 가 개발용 API 키입니다.
API 문서는 <http://localhost:8000/docs> 입니다.

Docker:

```bash
python scripts/gen_keys.py > .env
docker compose up --build
```

테스트와 평가:

```bash
python -m pytest -q
python eval/run_eval.py --n 20
```

## 사용 흐름

1. **원본 등록** — PDF 또는 이미지를 올립니다. (기업 문서 / 중고거래 사진 시나리오 선택)
2. **배포본 발급** — 수령자(사번) 또는 판매글 ID를 입력하면 토큰을 새로 발급해 워터마크가 들어간 파일을 내려받습니다.
   PDF는 페이지를 150DPI로 래스터화해 삽입한 뒤 같은 물리 크기의 PDF로 다시 만듭니다.
3. **유출 역추적** — 의심 이미지를 올리면 논문 그림 2의 판정 절차를 거칩니다. 결과에는 판정, 토큰 HMAC 색인 참조값, 원본 문서만 나옵니다.

   | 단계 | 아니오일 때 판정 |
   |---|---|
   | ① BCH 복호 성공? | 판정 불가 (재촬영) `undecidable` |
   | ② 발급 원장에 있는 토큰인가? | 미발급 토큰 (오탐 처리) `unissued` |
   | ③ 발급 원장 해시 체인이 무결한가? | 기록 위·변조 경고 `tampered` |
   | 모두 예 | 배포 대상 식별 `identified` |
4. **신원 열람** — 사유를 입력해야만 수령자 정보가 복호화되며, 열람 사실이 감사 로그에 남습니다.

## PDF 유형 분류와 유형별 삽입

원본 PDF를 등록할 때 자주 쓰이는 세 유형 중 하나로 자동 분류하고(`backend/app/pdf_utils.py`의 `classify_pdf`), 유형별 프로파일로 삽입합니다.
논문의 PSNR 38dB 조건 때문에 세 유형 모두 기본 강도를 씁니다(스캔형을 1.2배로 올리면 36.8dB로 떨어짐).

| 유형 | 판정 규칙 (문서 평균) | 삽입 강도 |
|---|---|---|
| 텍스트 보고서형 `text` | 아래 둘에 해당하지 않는 문서 (워드·한글에서 내보낸 세로 문서) | 기본 × 1.0 |
| 스캔·이미지형 `scan` | 이미지가 페이지의 85% 이상을 덮음, 또는 70% 이상이면서 텍스트 50자 미만 | 기본 × 1.0 |
| 프레젠테이션형 `slide` | 가로가 긴 페이지가 과반 | 기본 × 1.0 |

샘플 생성부터 토큰 발급·삽입·역추적 검증까지 한 번에 돌려 볼 수 있습니다. 결과는 `samples/RESULT.md`, 원본/배포본 비교 이미지는 `samples/preview_compare.png` 입니다.

```bash
python scripts/make_sample_pdfs.py     # samples/original 에 유형별 샘플 3개 (내용은 가상)
python scripts/demo_pdf_types.py       # samples/watermarked 에 배포본, data/ 에 토큰 기록
```

## 워터마킹 알고리즘 (논문 사양)

**발급** (`backend/app/services.py`)
1. CSPRNG로 24비트 토큰 생성 → HMAC-SHA256 색인 계산 (토큰 원문은 저장하지 않음)
2. 사용자 정보를 AES-256-GCM으로 암호화 (AAD = 색인·문서·발급 시각) → 발급 원장에 한 행 추가
3. 원장의 각 행은 직전 행의 SHA-256 해시와 연결 → 행을 고치거나 지우거나 끼워 넣으면 `/verify` 가 실패

**삽입** (`wm_core/engine.py`, `wm_core/bch.py`)
1. 24비트 토큰 → BCH(63,24) 부호화 (63비트, 7비트까지 정정)
2. 휘도 Y → 1단계 Haar DWT → LL 대역 → 8×8 블록 DCT
3. 블록마다 중주파 계수 쌍 (1,2)/(2,1), (1,3)/(3,1), (2,3)/(3,2)의 **대소 관계로 1비트** 표현 — 비트 1이면 앞 계수가 margin 이상 크게, 0이면 작게. 고주파는 쓰지 않음
4. 10×10 블록(160px) 타일 = 부호 63블록 + 동기 템플릿 37블록을 키 기반 순열로 배치, 페이지 전체에 **반복 삽입** (A4 150dpi 한 쪽에 약 70~80회)
5. 밝고 평탄한 **흰 배경 블록은 강도를 0.6배로 낮춤**. 기본 강도(margin 36)는 문서 PSNR 38dB 이상이 되도록 정함

**역추적**
1. 기하 보정: 그대로 → 등록 원본 크기로 리사이즈 → 페이지 경계 자동 검출 또는 사용자 지정 꼭짓점으로 원근 보정(4방향, ±2% 배율) → (정밀 탐색) 0.5~2배 배율
2. 배경 성분을 제거하고, 동기 템플릿과의 상관으로 블록 위치를 맞춤
3. 반복된 타일마다 계수 쌍 대소로 비트를 판정 → 비트별 **다수결** → BCH 복호
4. 그림 2 판정 절차 (사용 흐름 3번 표)

**우연 일치 확률**: 복원값이 무작위라면 발급 토큰 N개 중 하나와 일치할 확률은 N/2²⁴ (N=1,000일 때 약 6×10⁻⁵). 그 전에 무작위 63비트가 BCH 복호를 통과할 확률이 약 0.15%(시험 2만 회 실측)라 실제로는 더 낮습니다.

## 보안 설계

- 워터마크에는 무작위 토큰만 들어가며 토큰에서 신원을 계산할 수 없습니다.
- 발급 원장(`vault.db`)은 업무 DB(`app.db`)와 파일이 분리돼 있고, 사용자 정보는 AES-256-GCM으로 암호화돼 있습니다. 조회는 HMAC 색인으로만 합니다.
- 블록 배치와 동기 템플릿은 `WM_MASTER_KEY` 에서 유도되므로 키 없이는 추출할 수 없습니다.
- 신원 열람은 '배포 대상 식별' 판정이 난 기록만, 사유를 입력해야 가능하고 감사 로그에 남습니다.
- 한계: 해시 체인만으로는 관리자가 체인 전체를 처음부터 다시 계산해 바꾸는 것까지 막지 못합니다. 운영에서는 `/verify` 결과의 `head` 해시를 외부(타임스탬프 서비스, 별도 저장소)에 주기적으로 남겨야 합니다.

## 평가 결과 (합성 이미지 20장/조건, 기본 강도)

| 항목 | 결과 |
|---|---|
| 문서 PSNR / SSIM | 38.9 dB / 0.974 (논문 조건 38dB 이상 충족) |
| JPEG 30, 크롭 25%, 블러, 잡음, 밝기 변경, 리사이즈 | 20/20 |
| 크롭 10% + JPEG 50 | 8/20 |
| 화면 촬영 시뮬 (보통, 자동 검출) | 20/20 |
| 화면 촬영 시뮬 (강함·저해상도, 자동 검출 / 꼭짓점 지정) | 18/20 / 20/20 |
| 다른 토큰으로 잘못 복호된 횟수 | 0 |
| 워터마크 없는 이미지 오검출 | 0/40 |

전체 표(강도 0.8·1.0·1.2, 공격별 BER)는 `eval/results/report.md` 에 있습니다. 강도는 `WM_STRENGTH`(배율)로 조절합니다.
이전 버전(연판정 결합)보다 약한 조건이 있습니다: 크롭 10% + JPEG 50(18/20 → 8/20), 강한 촬영 자동 검출(20/20 → 18/20). 다수결은 경판정이라 연판정보다 정보 손실이 있고, PSNR 38dB 조건으로 강도를 낮췄기 때문입니다.

## 아직 검증하지 못한 것과 한계

- **실제 스마트폰 촬영은 시험하지 않았습니다.** 위 촬영 항목은 원근·모아레·블러·잡음·JPEG을 합성한 시뮬레이션입니다. 아래 절차로 실촬영 복원율을 직접 측정해야 합니다.
- **FastAPI 계층과 PyMuPDF 경로는 개발 환경에 해당 패키지가 없어 실행해 보지 못했습니다.** PDF 등록·발급·역추적 자체는 대체 백엔드(pypdfium2 + img2pdf)로 테스트를 통과했습니다. 패키지 설치 후 `python -m pytest -q` 로 `tests/test_api.py` 까지 확인하세요.
- 어두운 배경의 슬라이드(표지 등)는 촬영본에서 페이지 자동 검출이 실패할 수 있어 꼭짓점을 직접 지정해야 합니다.
- 촬영본은 페이지 네 변이 사진 안에 보여야 합니다(자동 검출 또는 꼭짓점 지정). 페이지 일부만 찍힌 사진의 회전·원근 복원은 지원하지 않습니다.
- 흰 배경에서는 확대하면 옅은 종이 질감처럼 보일 수 있습니다(이전 버전보다 옅음).
- 인증은 관리자 API 키 하나뿐입니다. 사용자별 계정·권한 분리는 없습니다.
- 한 타일(160px)보다 작은 조각에서는 추출할 수 없고, 2×2 타일 미만 이미지는 등록을 거부합니다. 작은 조각일수록 다수결에 쓸 반복 수가 줄어 복원율이 떨어집니다.

### 실촬영 실험 절차

```bash
python scripts/cli.py embed 원본.png 배포본.png          # 출력되는 24비트 token, size 를 기록
# 배포본.png 을 모니터에 띄우고 스마트폰으로 촬영 → 촬영본.jpg
python scripts/cli.py extract 촬영본.jpg --size 1240x1754
# 자동 검출 실패 시: --corners "x1,y1 x2,y2 x3,y3 x4,y4" (좌상 우상 우하 좌하)
```

거리·각도·밝기·기종별로 반복해 복원율을 `eval/results/` 에 기록하면 됩니다.
